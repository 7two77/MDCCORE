# MDC-WAL-001/1 — Wire format and commit protocol

2026-11-04. Specification version 1. A bounded implementation is described in
[MDC-IMPL-012](MDC-IMPL-012.md); execution scope and exclusions are stated there.
Scope: Linux, local filesystem, single writer, snapshot engine 011/1.
This fixes the first engineering profile of the owner's snapshot + WAL / hybrid
direction. The specification alone is not a runtime or power-loss test result.

## Store and identity

One store directory contains `LOCK`, `HEAD`, immutable snapshot generations
`S-<generation>.mdcs`, append-only WAL generations `W-<generation>.mdcw`, and
unpublished temporary files. Generation filenames use exactly 16 lowercase hex
digits of a u64. Paths are derived from numbers; wire data contains no paths.
Each store starts from an empty SnapshotSession with a frozen Registry. Import
of an already populated 011 session is outside this first host profile.

Session ID is 32 random bytes generated by the host at explicit create, fixed for
the entire history. It is a namespace, not authentication. Snapshot identity
profile is preserved: PortableV1 or legacy with the original width/endian checks.
Sequence is the number of core mutation calls, including semantic failures and
core idempotent calls. Host retries deduplicated before a core call consume no seq.

All multibyte integers are unsigned little-endian. `blob` is u64 byte length plus
exact bytes. `text` is a blob containing UTF-8. Checked arithmetic/conversions and
limits apply before allocation. Unknown tags/versions and trailing frame bytes
are errors. No native Rust serialization, Debug or Rust Hash enters this format.

## Common framing and integrity

Every frame is `magic[16] || version:u16=1 || body_length:u64 || body || digest[32]`.
Digest is SHA-256 of `domain || magic || version || body_length || body`.
Domains are the exact ASCII strings below, including the terminating zero byte.
The integer body_length excludes the 26-byte prefix and 32-byte digest.

| Frame | Magic, hexadecimal | Domain |
|---|---|---|
| Snapshot | `4d44432d534e502d3030310000000000` | `MDC-RECOVERY-001/snapshot/v1\0` |
| WAL header | `4d44432d57414c2d3030310000000000` | `MDC-RECOVERY-001/wal-header/v1\0` |
| WAL record | `4d44432d5245432d3030310000000000` | `MDC-RECOVERY-001/wal-record/v1\0` |
| HEAD | `4d44432d484541442d30303100000000` | `MDC-RECOVERY-001/head/v1\0` |

Checksums detect corruption under SHA-256 assumptions; no signature or MAC is
provided. A frame hash is its digest above. A file hash is SHA-256 of its entire
byte sequence, including frame digest. These two hashes are not interchangeable.
SHA-256 follows FIPS 180-4; host dependency choice is implementation work, not
permission to substitute FNV64 or invent a hash. Core remains dependency-free.

## Snapshot body, fields in order

`engine:u16=1, session_id[32], snapshot_generation:u64, snapshot_seq:u64,
core_snapshot:blob, receipt_count:u64, receipts[]`.

Each receipt is `seq:u64, request_id:text, request:blob, outcome:blob`.
Receipts are in seq order, exactly 1…snapshot_seq, with unique request IDs.
request_id has 1…256 UTF-8 bytes, no NUL; case and normalization are literal.
Receipt request/outcome must equal the corresponding saved 011 journal call;
snapshot operation_count equals snapshot_seq. No old host ID is pruned in v1.

The core snapshot is unmodified MDC-SNAPSHOT-001/1. The narrow core bridge must
expose exact journal request/outcome encoding and verified replay; it may not
allow arbitrary private Pipeline writes or a mutable escape. Existing private
operation tags 0…8 and outcome encoding from 011/engine1 are preserved.
External broker state, source cursor and order delivery are not fields of v1;
their transactional integration requires a separate consumer contract.

## WAL header body

`engine:u16=1, session_id[32], wal_generation:u64, snapshot_generation:u64,
base_seq:u64, snapshot_file_hash[32], base_state_hash[32]`.

base_seq equals the linked snapshot_seq. base_state_hash is SHA-256 of the exact
011 state_manifest bytes after restoring that snapshot. A WAL file starts with
exactly one header frame, followed by record frames without padding or gaps.

## WAL record body

`session_id[32], wal_generation:u64, seq:u64, request_id:text,
request:blob, outcome:blob, resulting_state_hash[32], previous_frame_hash[32]`.

First record seq = base_seq + 1, then increments by one with overflow rejected.
previous_frame_hash is the header frame hash for the first record, and the prior
record frame hash thereafter. resulting_state_hash is SHA-256 of exact 011
state_manifest after the call. Requests preserve input order and raw lookup
handles; outcomes include errors, not just success values. Commit must preserve
all host receipts and core audit multiplicity.

## HEAD body and sole commit authority

`engine:u16=1, session_id[32], head_generation:u64,
snapshot_generation:u64, snapshot_seq:u64, snapshot_file_hash[32],
wal_generation:u64, wal_base_seq:u64, committed_wal_bytes:u64,
durable_seq:u64, wal_tip_hash[32], durable_state_hash[32]`.

HEAD is one complete frame, exactly EOF. It selects a snapshot and ONE current
WAL generation. wal_base_seq = snapshot_seq. committed_wal_bytes is the file
offset immediately after the last committed frame, including the header.
durable_seq >= snapshot_seq; the committed prefix must contain exactly the
contiguous records through durable_seq. Empty suffix means offset = header size
and wal_tip_hash = header frame hash. durable_state_hash must match verified replay.

head_generation increments on every publication, including checkpoints that do
not change durable_seq. WAL has no independent commit marker in v1. No mtime,
record appearance or successful write advances D: only the selected HEAD defines
the committed range. This avoids guessing whether a damaged tail marker had once
been acknowledged. A corrupted HEAD is an error, not a reason to pick an older one.

## ACK and adapter state machine

Initial create: acquire exclusive writer lock, publish empty snapshot and WAL,
sync files and directory, then publish HEAD generation 1 at seq 0 via the protocol
below. Startup/open does not silently create a missing or damaged store.

| State / action | Required behavior |
|---|---|
| Open/usable | Exposes live seq L and durable seq D, L >= D |
| Buffered submit | Validate/budget candidate, append full record, publish provisional state, return AcceptedVolatile(seq, outcome) |
| barrier / commit_decision | Commit entire prefix through L; return DurableThrough(D) or CriticalCommit only after publication and sync |
| Already committed request ID, identical full request | Return the stored outcome/seq/durability; no new core call, record or audit |
| Existing volatile request ID, identical request | Return its volatile receipt; a requested strict retry must also complete barrier |
| Existing ID, different full request | Host RequestIdConflict, no mutation; digest alone is insufficient to compare requests |
| Indeterminate write/sync/publication error | Enter RecoveryRequired; no further mutation or decision publication, no durable ACK |
| Reopen | Validate HEAD and replay committed range in a fresh candidate before publishing usable state |

Semantic outcome (Pass/Fail/Unresolved or core error) is independent of storage
receipt. All nine mutations and semantic failures are recorded. A read of live
state is provisional if L > D. Decision barriers include all earlier inputs,
failures and receipts; selective flush of Evaluation alone is forbidden.
No scheduling threshold is frozen: interval/N are explicit host configuration.
No background task may claim a durable ACK merely because a timer expired.

## Strict publication and error boundary

Hold Linux nonblocking exclusive flock on the persistent LOCK file for the entire
open lifetime; second writer fails. Never unlink/recreate LOCK while a store exists.
Process death releases the OS lock; PID-file deletion is not the lock mechanism.
The host binding must support MSRV 1.85.1; newer std-only lock APIs are not assumed.

For a barrier, block concurrent submits and bind an immutable candidate at L:

1. Finish all complete WAL records through L. Call WAL sync_all successfully.
2. Create HEAD temporary file exclusively in the same directory. Encode complete
   next HEAD pointing at this exact prefix; write all bytes, sync_all the temp file.
3. Atomically rename temp over HEAD. Call sync_all on the containing directory.
4. Publish in-memory D = L and return durable receipt. A lost response after commit
   is resolved by request ID on reopen. No external trading action precedes receipt.

New WAL/snapshot filenames must already be file-synced and directory-synced before
HEAD can reference them. ACK follows ALL relevant sync calls. Errors after I/O
starts are conservatively RecoveryRequired, with no claim of rollback. Validation
or limit errors before I/O leave the store usable and unchanged. A failed candidate
must not leak into accessible live state. Full candidate replay/copy is acceptable
for the first bounded implementation; its performance must be measured.

If interruption occurs before ACK, old OR new valid HEAD may be recovered. A
published but unacknowledged complete generation is allowed. Missing or corrupt
referenced files, HEAD integrity failure or invalid committed prefix fail closed.

## Recovery and checkpoint/rotation

Read/validate HEAD first. Validate the selected snapshot by full file hash, restore
its core state and receipts, then validate WAL header and only bytes through the
committed offset. Replay every committed record using production APIs; require
exact outcome, frame chain, per-record state hash, seq and receipt uniqueness.
Require final tip/state/seq equal HEAD. Unknown versions/profile/environment
mismatches fail closed; no new semantic interpretation or legacy migration.

Bytes after committed_wal_bytes are uncommitted even if valid frames. They are
not replayed. Before resuming append, remove that suffix under lock and sync the
WAL. Errors block open. Corruption inside the committed range must never be
treated as a torn tail. Files shorter than the committed offset are corruption.
Ignore unrelated temporary/orphan files; never promote them by filename or mtime.

Checkpoint first commits all live history so L = D. Write a new full snapshot at
D with all retained host receipts; sync it and a new WAL header based at D, then
sync directory. Publish next HEAD selecting this pair, with header-only WAL prefix.
Only after HEAD directory sync may older generations be deleted; sync cleanup.
Recovery must also sync the selected HEAD directory before cleanup: a prior
process may have died after rename but before that directory sync. Generation
files use exclusive creation, never overwrite. Snapshot/WAL generations increase
across committed checkpoints; orphan-name conflicts are diagnosed or removed
under lock only after the selected committed pair is proven and directory-synced.
Crash before publication retains the old pair; after publication uses the new
pair. Sequence and request IDs never reset. Deleting WAL does not compact the
entire recorded core history stored by 011.

## Logical defaults and exclusions

First adapter defaults: max frame body 64 MiB; core snapshot uses 011
limits (16 MiB archive default); request/outcome blobs each <= 2 MiB; request IDs
<= 256 bytes; max live operations/receipts 4096; WAL file <= 64 MiB; HEAD body <=
4096 bytes. Snapshot receipt totals also fit frame cap. Enforce bounds before
allocation/I/O, checked seq/generation/offset arithmetic, no silent truncation.
These logical caps do not provide hard OOM, CPU or hardware latency guarantees.

Integrity vectors in evidence/wal-framing-v1.json fix common framing only. Their
opaque bodies are not valid core histories and do not prove semantic recovery.
Unknown version, length bombs, bit flips, chain breaks, conflicting IDs, committed
corruption, lost ACK, writer contention and kill at every publication/rotation
boundary must be tested in the runtime implementation (R01…R12).

sync_all requires supported filesystem, driver/controller and device flush
semantics. Process-kill/fault tests do not establish universal real power-loss
durability. NFS, multiple writers, source cursor transactions, authentication,
exactly-once order delivery, history pruning and temporal availability are excluded.
